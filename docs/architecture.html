    Plugin API Lifecycle

    1. v1 current — MVP ships plugin API v1.
    2. v2 introduced — both supported; docs prefer v2.
    3. v1 deprecated — runtime warning once per session; CI lints for first-party.
    4. v1 removed — only on product major (e.g. 2.0); migration guide required.

    Minimum deprecation window: one stable product minor or 90 days, whichever longer (except security emergencies).

    Memory Ownership

    Rust correctness at IDE scale depends on explicit ownership. Default: one owner, many borrowed readers, Arc only at process/service boundaries. See ADR-0012.

    Who Owns What

    Object Owner Shared how Clone policy Notes
    Buffer text (rope) nvide-core BufferRegistry ID handles across processes; snapshots as immutable bytes/rope chunks Never clone full rope casually; prefer slice / snapshot handles Single-writer in core
    Buffer metadata / version Same as buffer Copy small structs Copy OK Monotonic version for LSP

    Session / workspace Core Session Arc<SessionCfg> for immutable config OK Config Arc; live state exclusive Persisted to disk separately
    Extmark tree Buffer (core) Query results as owned Vec No shared mutable tree across threads without lock Interval tree private

    NRPC connections Each process runtime Arc<Connection> inside process Arc clone for tasks OK No raw fd sharing without wrapper

    Arc / Rc / Mutex Rules

    • Rc / RefCell: single-threaded UI or single-threaded subsystems only; never across await points that may move threads.
    • Arc: cross-thread immutable data, connection handles, service registries. Prefer Arc<T> where T is immutable or uses interior mutability sparingly.
    • Mutex / RwLock: short critical sections; no lock held across IPC await. Prefer message-passing to shared mutable state.
    • Forbidden: Arc<Mutex<Buffer>> shared into UI for live editing — edits go through core commands only.
    • Snapshots: for async consumers (LSP, search), take versioned immutable snapshots; drop if version mismatched on apply.

    Error Philosophy

    Unify failure handling early so contributors do not invent per-crate conventions. See ADR-0013.

    Error Classes

    Class When Mechanism User-visible Example
    Expected / recoverable IO, user input, network, plugin faults Result<T, E> + typed errors (thiserror) Toast / panel / inline File not found; LSP crash; SSH drop
    Degraded mode Optional subsystem down Result + feature flag / banner state Persistent status segment Git host restarting; lang host down
    Invariant violation (debug) Internal bug detected in debug builds debug_assert! / checked returns Dev-only Extmark offset past buffer end after fixup bug
    Fatal process Unrecoverable process corruption Controlled abort after flush WAL; supervisor restarts Crash report prompt Core allocator corruption; UI GPU device lost loop
    Panic Truly unreachable OR library panic Catch at process boundary (catch_unwind only at host edges); never across FFI unchecked If escapes: process restart Plugin host isolates panics per task where possible

    Hard Rules

    • Public / Friend APIs return Result; do not panic on user data.
    • unwrap() / expect() only when invariant is locally proven; comment why; banned in hot paths without lint allow.
    • IPC errors are always recoverable at the caller; never panic the UI thread for a failed plugin RPC.
    • Logging: error! for recoverable ops failures; error!+metrics for restarts; no PII in logs by default.
    • User-facing strings are separate from machine error codes (nvide.error.fs.not_found).

    Executive Summary

    What is NVide?

    NVide is a from-scratch native IDE written in Rust. It is not a Neovim fork, not a VS Code fork, and not an Electron application. It targets developers who want the speed and modal editing DNA of Neovim with the structured IDE features of VS Code / JetBrains — without the memory tax of Chromium or the C/Lua inheritance constraints of Neovim.

    The product differentiates on four pillars:

    1. Native performance — sub-100 ms cold UI shell, multi-GB files via rope buffers, 120 Hz GPU UI.
    2. Lua-native configuration — init.lua is first-class; no Vimscript ever.
    3. Compatibility without cloning — a translation layer presents a vim.* surface to plugins while the core uses clean Rust APIs.

    Non-Goals (Strategic)

    • Embedding or forking Neovim’s C core.
    • Running Electron / Chromium for primary UI.
    • 100% bug-for-bug Neovim API parity (see compatibility tiers).
    • Supporting Vimscript.
    • Being a pure terminal TUI (GUI is primary; headless mode is secondary).

    Vision & Design Principles

    Architectural Principles

    P1 — Process Isolation First

    UI, core, plugins, language servers, and remote hosts never share an address space unless explicitly opted in. A plugin crash must never take down the editor.

    P2 — Stable Surfaces, Flexible Internals

    Public APIs (Rust crate versions, Lua nvide.*, compat vim.*, RPC protocol) versioned independently of internal refactors.

    P3 — Lua Is Configuration DNA

    Every user-facing setting, keymap, and plugin entry point is expressible in Lua. No parallel config language.

    P4 — Compatibility Is a Layer, Not the Core

    The editor core never speaks Neovim. A dedicated compatibility service translates. Core stays clean and independent of plugin-ecosystem churn.

    P5 — Measure, Then Ship

    Performance budgets are enforced in CI. No regression without an ADR waiver.

    System Overview

    High-Level Topology

    NVide is a multi-process, message-oriented IDE. The GUI process is thin; durable state and language intelligence live in workers. Communication uses a versioned binary RPC (Cap’n Proto or similar; see Multi-Process / IPC, ADR-0002) over local IPC (Unix domain sockets / named pipes) and over the remote transport when the workspace is remote.

    Process Roles

    Process Binary Responsibility Crash impact Restart policy
    UI nvide Window, input, GPU render, layout Session ends (state in core) User relaunch; core may persist
    Core nvide-core Editor state, config, orchestration Critical; autosave/recovery Supervisor relaunch + recovery
    Plugin host nvide-plugin-host Lua/Rust/WASM plugins Plugins only Per-plugin or full host restart
    Lang host nvide-lang LSP/DAP client lifecycle IntelliSense gap Auto restart servers
    Git host nvide-git Status, diff, blame, ops SCM UI stale Auto restart
    Terminal host nvide-term PTY / ConPTY sessions Terminals die Optional restore
    Remote agent nvide-agent Remote FS/LSP/PTY/Git tools Remote workspace offline Reconnect + resume
    Architecture Decision — Supervisor model

    Why: Long-lived IDEs need supervised children. A thin supervisor (embedded in core or a tiny parent) owns lifecycle, crash dumps, and restart budgets.

    Alternatives: Single process (rejected — crash blast radius); OS service managers only (rejected — poor Windows/macOS UX parity).

    Migration: Processes speak a versioned handshake; new process types can be added without UI changes.

    Primary Data Flows

    Sequence diagrams: Event Flows.

    1. Typing path: UI key event → core keymap → buffer mutation → dirty viewport → UI paint commands (glyph runs + decorations).
    2. Plugin path: Core event bus → plugin host RPC → Lua callback → core API → state change → UI.
    3. LSP path: Buffer change → debounced didChange → lang host → server → diagnostics/completion → core → UI overlays.
    4. Remote path: Same logical RPCs; transport is multiplexed over SSH/WSL/Docker; agent executes FS/PTY/LSP locally on remote.

    Multi-Process Architecture & IPC

    IPC Protocol Design

    All inter-process communication uses NVide RPC (NRPC) — a framed, multiplexed, bidirectional protocol.

    Wire format

    • Transport: Unix domain sockets (Linux/macOS), named pipes (Windows), vsock/SSH channel (remote).
    • Framing: length-prefixed messages (u32 LE) + stream id (u32) + flags (u16) + payload.
    • Serialization: Cap’n Proto (zero-copy reads) for hot paths; MessagePack allowed for plugin Lua bridge convenience.
    • Streams: multiplex request/response, server push, and binary blobs (file chunks, terminal bytes).
    • Versioning: major.minor in handshake; minor is backward compatible; major requires dual-stack or upgrade. 
    NRPC Frame
┌──────────┬──────────┬────────┬────────────────────────────┐
│ len u32  │ stream   │ flags  │ payload (Cap'n Proto/msg)  │
│          │ id u32   │ u16    │                            │
└──────────┴──────────┴────────┴────────────────────────────┘
Flags: REQ | RESP | PUSH | ERR | CANCEL | COMPRESSED | PRIORITY

    Message categories

    Category Examples Latency budget Ordering
    Input / edit KeyEvent, ApplyEdit < 2 ms local Strict per-buffer
    UI paint ViewportSnapshot, Decorations < 8 ms Latest-wins coalesced
    LSP Completion, Diagnostics 50–200 ms Per-request cancelable
    FS Read, Write, Watch varies Per-path queue
    Terminal PTY bytes streaming Byte-ordered stream
    Performance — Coalescing

    UI paint and diagnostic pushes are coalesced. Only the latest viewport for a window is rendered. Edit events are never dropped but may batch under high load with deterministic merge of adjacent inserts.

    Failure Recovery

    • Heartbeat: 1 s ping; 3 missed → unhealthy; 5 s → restart child.
    • Crash dump: minidump/breakpad-style; uploaded only with user consent.
    • State durability: core writes WAL for buffers (see crash restore); plugins rehydrate from disk manifests.
    • Restart budgets: exponential backoff; after N crashes in window, quarantine plugin or disable feature with user notification.
    • Partial degradation: UI remains usable without git/lang; banners indicate degraded mode.

    Developer Escape Hatch

    For debugging, NVIDE_SINGLE_PROCESS=1 embeds hosts as threads/tasks. Not for production releases. Keeps the same API surface so tests can run both modes.

    Architecture Decision — Layered crates

    Why: JetBrains Platform and VS Code both suffer when “the app” is one blob. Explicit crates force API thinking.

    Pros: parallel CI, clear ownership, testability, future extraction (e.g. buffer as library).

    Cons: more boilerplate, version coordination.

    Migration: crates can split further; public plugins bind only to nvide-plugin-api semver.

    Decision: winit + wgpu + custom UI toolkit (nvide-ui / nvide-render)

    Status
    Accepted (ADR-0003)
    Why
    Maximum control for text rendering, multi-window, high-DPI, and long-term ownership of the rendering stack. Avoids WebView and external framework risk. Matches the performance bar of WezTerm/Zed without adopting another product’s UI framework as a dependency.
    Alternatives rejected
    Tauri (violates native/no-Electron spirit), pure egui (a11y + IDE density), GPUI (coupling/churn).
    Mitigation
    Borrow proven algorithms (glyph cache, atlas, damage regions) from open literature and open-source; do not invent text shaping. Use cosmic-text / swash / HarfBuzz bindings for shaping.
    Migration
    UI toolkit is internal. If a mature Rust UI framework becomes clearly superior later, reimplement widgets against the same retained scene graph interface — core never paints.
    Scalability
    Scene graph + damage tracking scales to multi-monitor 5K and many splits; GPU path is the long-term bet.
    Recommendation

    Invest early in a small, excellent retained-mode toolkit (layout, focus, a11y tree, virtualization). Prototype with egui only for internal debug panels if needed — never for the product shell.

    • Animation: 150–200 ms ease for panels; respect prefers-reduced-motion.

    Accessibility, DPI, multi-monitor

    • Platform accessibility bridges (UI Automation / NSAccessibility / AT-SPI) for chrome; editor content exposes caret/selection via platform APIs where feasible.
    • Per-monitor DPI; fractional scaling on Linux; crisp text via subpixel or grayscale AA selectable.
    • Multi-window: each window owns a GPU surface; shared core session.

    Editor Core

    Buffer Model

    A Buffer is the unit of editable text. Buffers may be file-backed, anonymous, or virtual (diff, preview).

    Piece Table vs Rope

    Structure Pros Cons Complexity Performance Maintainability Scalability Migration
    Piece Table Simple undo; great for sequential edits; used by VS historically Degrades with random access without index; line lookups need cache Low–Med Good small/medium High Needs secondary index for large files Medium
    Rope (recommended) O(log n) split/merge; strong for huge files; chunked concurrent reads More complex; careful UTF-8 boundaries Medium Excellent large files High with mature crate Excellent Trait-based swap possible
    Gap Buffer Fast local edits Poor multi-cursor / large jumps Low Local only High Poor Low

    Decision: Rope with line index cache (nvide-buffer)

    Status
    Accepted (ADR-0005)
    Why
    Large-file and multi-cursor workloads dominate IDE life. Rope (e.g. based on ropey algorithms, possibly forked/custom for CRDT-friendly ops later) wins on asymptotic behavior.
    Design
    Buffer trait: insert, delete, slice, line, line_count, char_to_byte. Default impl: rope + line starts index + optional chunk mmap for read-only huge files.
    Migration
    All core code depends on Buffer trait, not concrete rope. Can introduce piece-table backend for tiny scratch buffers if profiling warrants. 
    pub struct BufferId(u64);

pub struct Buffer {
    id: BufferId,
    text: Rope,
    line_index: LineIndex,
    encoding: Encoding,
    file: Option<FileMeta>,
    dirty: bool,
    version: u64,           // monotonic for LSP
    marks: MarkMap,
    extmarks: ExtmarkTree,  // interval tree
    undo: UndoTree,
    read_only: bool,
}

    Cursor, Selection, Multi-Cursor

    • Cursor: (buffer_id, point) where point is (line, col) + affinity (before/after grapheme).
    • Selection: ordered range with anchor + head; supports block (rect) selection.
    • Multi-cursor: list of carets; edits applied as a single transactional batch with shared undo node.
    • Columns are display columns for rendering and char indices for buffer ops — conversion layer handles tabs/wide glyphs.

    Registers & Macros

    • Named registers (a–z, A–Z append), unnamed, clipboard alias (+/*), expression, search, black hole.
    • Macro recorder stores key event stream (not resolved actions) so remaps can be handled consistently; optional “resolved action” mode for robustness.
    • Registers serialize into session for restore.

    Undo Tree

    Branching undo tree (not linear stack), inspired by Neovim/Vim undo trees and modern editors.

    • Each node: inverse operations + timestamp + cursor snapshot.
    • Coalescing: typing within timeout merges nodes; explicit breakpoints on mode change / paste / external edit.
    • Persistent undo: optional disk-backed undo history per file hash.

    Viewport & Scrolling

    • Viewport = visible line range + horizontal scroll + fold map + wrapped line cache.
    • Scrolling: pixel-smooth optional; default line-based for modal users.
    • Virtual lines for folds, inlay hints, virtual text.
    • Damage regions: only re-shape and re-upload dirty glyph runs.

    Rendering Pipeline

    Performance

    Target: shape only visible ± overscan lines. Cache shaped lines by (buffer_version, theme_gen, width). Large files never fully shape.

    Syntax Highlight & Tree-sitter

    • Tree-sitter for incremental parse; grammars loaded dynamically.
    • Highlight queries produce capture ranges → theme mapping.
    • Async parse on background thread; apply when version matches.
    • Semantic tokens from LSP overlay and win on conflict when enabled.
    • Injection languages (markdown code blocks, SQL in strings) supported via TS injections.

    Extmarks, Virtual Text, Folds

    An extmark is an anchored decoration/range that survives edits (Neovim-compatible concept, independent implementation).

    • Stored in interval tree keyed by buffer byte positions with gravity.
    • Uses: diagnostics underlines, search matches, breakpoints, coverage, inlay hints, virtual text lines.
    • Folds: tree of fold ranges; provider from treesitter, LSP, indent, manual.

    Search & Replace

    • Buffer search: literal, regex (Rust regex), smartcase; multi-cursor “select all matches”.
    • Project search: streaming ripgrep-class engine in nvide-search; respects gitignore; remote agent runs search on remote FS.
    • Replace all: transactional multi-buffer edits with single undo group option.

    Jump List, Marks, Windows, Tabs

    • Jump list: per-window history of positions; tagged jumps from LSP/goto.
    • Marks: local a–z, global A–Z, numbered; file+position persistence.
    • Windows: splits in editor groups; layout tree (row/col nodes).
    • Tabs: editor group tabs + optional “tab pages” for workspace layouts (Neovim-like).

    Workspace, Session, Autosave, Recovery

    • Workspace: multi-root folders, trust state, tasks, launch configs, layout.
    • Session restore: open buffers, cursors, folds, layout, terminal CWDs (not secrets).
    • Autosave: configurable debounce; never saves unsaved “Untitled” without path.
    • Crash recovery: WAL of unsaved buffer snapshots under user data dir; restore wizard on next launch.
    • Swap/recovery files: per-file recovery blobs with mtime/hash checks.

    Clipboard

    • System clipboard via platform APIs; optional OSC 52 for remote terminals.
    • Internal ring history (yank history) independent of OS clipboard.
    • Large clipboard payloads: async set to avoid UI jank.

    Neovim Compatibility Layer

    Philosophy

    NVide is not Neovim. It implements a compatibility façade that presents a familiar vim global to Lua plugins. Internally, every call translates to NVide core operations. We maximize practical plugin compatibility without cloning Neovim internals, Vimscript, or C structures.

    Compatibility — Estimated ceiling

    Realistic long-term estimate: ~70–85% of pure-Lua plugins that stick to documented Neovim APIs. Plugins that depend on Vimscript, undocumented C internals, specific buffer implementation quirks, or vim.loop FFI will fail unless rewritten.

    MVP estimate: ~35–45% of popular pure-Lua plugins with Tier A APIs implemented; rising as tiers expand.

    Compatibility Levels

    Level Meaning Examples Support commitment
    L0 — Native NVide-first API nvide.buf, nvide.cmd Full, versioned
    L1 — Core compat Faithful enough for most plugins vim.api buffer/window, vim.keymap, vim.opt, vim.notify, vim.schedule High priority
    L2 — Extended Common but deeper vim.lsp, vim.diagnostic, vim.ui, vim.treesitter Phased
    L3 — Emulated Behavioral subset / polyfill parts of vim.fn, vim.loop subset Best-effort
    L4 — Unsupported Will not implement Vimscript, :python, RPC UI protocol as Neovim, internal C structs None

    API Surface Design

    vim.api — L1

    Implement as thin wrappers over core buffer/window/tabpage IDs. Maintain Neovim-like integer IDs via mapping tables (NVide UUID/u64 ↔ compat int).

    • Buffer: create, delete, get/set lines, get name, set option, attach events (streamed as Lua callbacks).
    • Window: open/close, get cursor, set cursor, get buf, config for floats.
    • Extmarks: full namespace API mapped to NVide extmark tree.
    • Autocmds / commands / keymaps: registered into core event system.

    Do not emulate: exact error strings, every edge-case of deprecated APIs, channel/job control identical to Neovim unless needed.

    vim.fn — L3 (selective)

    Hundreds of functions exist in Vim. Strategy: implement by demand analytics from popular plugins. Categories:

    • Must: expand, fnamemodify, glob, filereadable, json_encode/decode, stdpath, getcwd, has, executable.
    • Should: system/systemlist (permission-gated), bufadd, bufname, line, col.
    • Won’t: obscure legacy, GUI Vim-only, Vimscript-eval based.
    vim.loop — L3 (subset of libuv)

    Expose async FS, timers, TCP/pipe via host-mediated APIs — not raw libuv FFI. This is critical for sandboxing. Plugins using ffi to touch libuv directly are unsupported.

    Map to Rust async runtime (tokio) in plugin host.

    vim.ui — L2

    vim.ui.select, vim.ui.input → native UI widgets in UI process via RPC. Plugins get callbacks when user completes.

    vim.lsp / vim.diagnostic — L2

    Do not reimplement language servers inside Lua. Bridge to nvide-lsp / diagnostic store. Provide Neovim-shaped client object enough for nvim-lspconfig-style configs and common plugins (trouble.nvim-class UIs).

    Some plugins assume Neovim’s exact client lifecycle; provide adapters and first-party nvide-lspconfig as the recommended path.

    vim.notify / vim.schedule / vim.keymap / vim.opt — L1

    High value, relatively small surface. vim.schedule queues onto plugin host main loop. vim.opt mirrors settings store with metatables for .get/.set/.append.

    vim.g / vim.b / vim.w / vim.bo / vim.wo — L1/L2

    Global and scoped variables stored in core maps; buffer/window options validated against schema. Unknown options: store but warn once (compat for plugins setting obsolete opts).

    vim.treesitter — L2

    Wrap NVide’s tree-sitter service: parsers, queries, highlighters. Language tree objects are handles, not raw C pointers. FFI to parser C APIs unsupported.

    Translation Architecture

    What to emulate: documented Lua API behavior, option names popular plugins need, autocmd event names, floating window config fields.

    What not to emulate: Vimscript engine, Neovim UI protocol clients, exact memory layout, every historical bug, vim.mpack edge cases, provider frameworks for clipboard/python.

    Maximizing Compatibility Without Cloning

    1. Maintain a plugin compatibility test suite that installs top N plugins and runs smoke tests.
    2. Telemetry (opt-in): which vim.* functions fail most — drive backlog.
    3. Ship NVide-native ports of critical plugins (statusline, fuzzy finder, file tree) as gold standards.
    4. Publish a compatibility matrix site (generated from CI).
    5. Provide nvide.compat.report() for users to see unsupported calls in their config.

    Remote Development

    Model (VS Code–like)

    UI always runs locally. A remote agent runs where the code lives (SSH host, WSL, Docker/Dev Container). Core may run local (thin client mode) or co-located with agent for latency (optional advanced mode). Default: local core + remote agent for simpler crash domains; evaluate co-location if latency demands.

    Decision: Local UI + local core orchestrator + remote agent for FS/PTY/LSP/Git tools

    Why
    Matches VS Code remote architecture familiarity; keeps GPU UI local; minimizes remote GPU needs.
    Tradeoff
    Edit latency is local; file IO is remote. Buffer text is cached locally with version vectors.
    Alternative
    Full remote core (lower consistency risk, higher reconnect complexity). Deferred to post-MVP if needed.

    Transports

    Scenario Transport Notes
    Windows → WSL localhost socket / AF_UNIX via Windows / named pipe bridge Auto-detect distro; install agent into WSL
    Windows → Docker Docker exec + port/socket mount Dev Containers metadata
    Windows/macOS/Linux → SSH SSH multiplexed channel or reverse tunnel ControlMaster-like reuse
    Dev Containers Build/start container → attach agent devcontainer.json support

    Remote Protocol

    Same NRPC schema as local IPC, with extensions:

    • fs.* — open, read, write, rename, watch, stat, copy (chunked).
    • pty.* — open, input, resize, signals.
    • lsp.* / dap.* — process control; stdio framed.
    • git.* — ops against remote repo.
    • task.* — run builds/tests on remote when requested.
    • agent.health — heartbeat, capabilities, version. 
    Local UI/Core                         Remote Agent
    │                                      │
    │  HELLO(version, auth, caps)          │
    │─────────────────────────────────────►│
    │  HELLO_ACK(session, caps)            │
    │◄─────────────────────────────────────│
    │  FS_WATCH(root)                      │
    │─────────────────────────────────────►│
    │  FS_EVENT(...)                       │
    │◄─────────────────────────────────────│
    │  PTY_OPEN / LSP_START / ...          │
    │◄────────── streams ─────────────────►│

    Isolation, Reconnect, Offline

    • Process isolation: agent is separate binary; compromised plugin on remote does not auto-own local machine (still treat remote code as trusted-as-workspace).
    • Reconnect: session tokens; resume FS watches; reattach PTY if OS allows, else restore with message; LSP restart with document sync from local buffer cache.
    • Offline behavior: local buffer edits continue; queue writes; mark workspace offline; conflict detection on reconnect (mtime/hash).
    • Failure recovery: exponential backoff; user-visible connection strip; “Reopen in local” escape.

    Security

    Threat Model (Summary)

    • Malicious plugins from marketplace.
    • Malicious workspace files (scripts, tasks, LSP configs).
    • Remote host compromise.
    • Supply chain attacks on updates.

    Workspace Trust, Secrets, Signing

    • Workspace trust: untrusted workspaces disable tasks, plugins auto-run, and agent tools until trusted.
    • Secrets: OS keychain (Windows Credential Manager, macOS Keychain, libsecret/Secret Service); never plain-text tokens in config.
    • Credential storage: git credentials via OS / gh / git-credential helpers, not reinvented.
    • Marketplace verification: package signatures (ed25519), publisher verification, SBOM, malware scanning in registry pipeline.
    • Auto-update signing: minisign/cosign-style signatures on release artifacts; update client verifies before apply.
    Warning

    Compatibility with Neovim plugins increases risk: many expect shell and unrestricted FS. Default sandbox will break some plugins — document clearly; offer “legacy unrestricted” profile for power users with explicit warning.

    Appendix

    Native Keymap Engine Notes

    Implement a pure Rust modal engine with:

    • Operator-pending mode, counts, registers.
    • Which-key style discovery via command metadata.
    • Lua remaps that never re-enter infinite recursion (Neovim-like remap/noremap).
    • Timeoutlen / ttimeoutlen equivalents.

    Do not shell out to Vim for motions.
