    Canonical plan and review state

    The Markdown plan is canonical. This HTML may shorten prose but must preserve every normative gate, stable ID, interface, metric, exclusion, and ADR mapping. Two qualifying independent artifacts review both formats at commit 710644906cd9589c2e3f2c25a8484088e710feac.

    Plan governance

    • Architecture v0.2.1 and Accepted ADR-0001…ADR-0019 remain authoritative.
    • A requirement absent from Architecture becomes a prerequisite decision or artifact; implementation does not guess it.
    • The phase lead owns prerequisites unless a narrower owner is named. ADRs use the Architecture acceptance rule. Other artifacts require the phase lead and one independent reviewer; security artifacts also require a security reviewer.
    • Human and AI agents may fill reviewer roles. Record principals as human:<handle> or agent:<canonical-task-id>. Every reviewer principal must differ from every author or implementer and every other required reviewer; for AI, another turn by the same agent is not independent, and one agent cannot fill multiple required reviewer slots.
    • Each phase creates the named evidence ledger during implementation. Every entry records its stable requirement/acceptance ID, artifact path, command, environment/profile, result, date, and reviewer principal. Review records also name every author or implementer principal and exact reviewed commit; the inspectable review artifact itself identifies the reviewer principal, verdict, reviewed commit, and review scope. A claim without a runnable command or inspectable artifact is not exit evidence.
    • IDs are immutable after review: prerequisites use Pn.n, requirements Pn-Rn, acceptance Pn-An, evidence Pn-En, and blockers Pn-Bn; 6A–6D use their milestone prefix. CI must reject duplicate/unknown IDs and required IDs without ledger references.
    • A phase starts only after dependencies and all prerequisites are approved. Phase 4 may overlap Phase 3 only after Phase 2 exits.
    • Two inspectable, independent review records cover both formats, Phase 0–5, and the Phase 6+ umbrella at the reviewed commit; both AI records satisfy the distinct-agent rule.

    Sequencing and scope

    1. Protect Phase 0 buffer, rendering, IPC, supervisor, and cross-platform baselines before product features.
    2. Do not scaffold later-phase crates or pull plugins, LSP, Git, terminal, remote, marketplace, DAP, or WASM into an earlier phase.
    3. Phase 3 and Phase 4 may overlap only after Phase 2; Phase 5 requires successful exit of, then integrates and revalidates, Phases 0–4.
    4. Apply ADR-0018's relevant unit, integration, snapshot/golden, fuzz, compatibility, performance, and cross-platform gates in every phase.
    5. 6A–6D are separate approvals. CRDT, NRPC v2, renderer replacement, and LuaJIT stay research-only until demand and an Accepted ADR authorize them.

    MVP boundary

    Included: native UI; approved modal editing; rope, multi-cursor, undo, search, splits/tabs; selected Tree-sitter languages; Lua configuration; Lua plugin host and Compat L1; seven LSP features; local terminal; hybrid Git; recovery; basic SSH; required installers.

    Excluded: WASM, full DAP, WSL/Docker/Dev Containers, full Neovim compatibility, Vimscript, collaboration, automatic merge-conflict resolution, mobile/web, full marketplace PKI, delta updates, and pixel-perfect VS Code theme import.

    Locked interface

    • Manifest: identity, version, source, dependencies, permissions, activation.
    • Lockfile: commit/version/hash.
    • Lifecycle: discover → resolve → fetch/verify → load → activate → runtime → deactivate → quarantine.
    • Defaults: workspace-only read; prompt write/clipboard; deny net/shell. UI allow means declarative contribution, not editor-state read. LSP is a bounded API, not raw transport/server access. Neither permits arbitrary buffer/workspace/source reads without explicit content-read grant. Activation/grants require workspace trust; grants are revocable; legacy unrestricted is opt-in with warning.
